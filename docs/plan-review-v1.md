以下、ChatGPT の計画を「計画」、その段階の名前を「計画 M0〜M8」と書く。**このリポジトリの段階名（M2 = ガルドロスを狩って帰る、M3 = 里と生産と保存）とは番号が違う**ので注意。

## 0. 結論

1. **計画 M0〜M2 は、すでに満たしている。** 計画は v0.3.4 の時点の資料をもとにしており、いまは v0.5.1。断岳剣の共有値（72 tick、判定 [22,30)、回避接続 [58,72) など）は全部そのまま入っていて、自動テストで確かめている（4 章）。
2. **計画 M3（ガルドロス）も大半が入っている。** 4 攻撃・頭と背殻の破壊・尾の切断・怒り・転倒・捕獲・剥ぎ取り・報酬まで。技は 4 つではなく 23 ある。
3. **足りないのは計画 M4 の後半と M5。** 保存、強化 1 件、研磨石と刃の状態、再読込後の復元。実機での計測。**「1 回の狩猟を、再読込まで通す」という計画の最初の到達点は、まだ達成していない。**
4. **計画と食い違う一番大きな点は武器。** 計画は 5 系統（旋鎌を含む）が前提だが、利用者の指示で旋鎌をやめ、大槌・双剣・太刀を足して 7 系統になった（v0.5.0、D-055）。素材の一覧のうち旋鎌に関わる行は読み替えが要る（6 章）。
5. **採用する方針（D-056）**: これ以上、武器や技を横に増やすのは止めて、次は「保存 → 強化 1 件 → 研磨石と刃 → 実機の計測」の順で、1 回の狩猟を最後まで通す。

**今回入れた小さな差分（v0.5.1）**

- **描画の間隔の計測**（`src/core/frameMeter.ts`）: 平均・p95・最大・100ms を超えた回数を記録する。検証表示と、メニュー「検証」の報告用の欄に出る。iPhone で 1 分ほど遊んでからメニューを開き、「コピー」で数値を持ち帰れる。止まっていた間（メニュー・非表示）は数えない。「計測をやり直す」ボタンあり。

## 5. 計画の採否

**採用する**

- 最初の到達点「受注 → 準備 → 狩猟 → 剥ぎ取り / 報酬 → 帰還 → 強化 1 件 → 再読込後の復元」を、次の目標にする。順番は **(1) 保存 → (2) 強化 1 件 → (3) 研磨石と刃の状態 → (4) 実機の計測**。
- 保存の作り方（13 章）: 既存の localStorage の設定を消さない。持ち物・通貨・進行・処理済みの依頼 runId・revision を 1 つの transaction で更新し、完了してから成功を表示。revision が合わなければ上書きしない。JSON の書き出し / 読み込み。未知の ID は捨てずに保留。「永久に保存」とは書かない。
- 状態の分け方（原画: 生成済み / 確認済み / 採用済み / 組込済み。3D: 形状 / リグ / 動作 / 組込）。すでに `docs/asset-manifest.json` がこの形。
- 画像の発注と納品の決まり（17 章）。1 枚ずつ本文に表示、ファイル名、表示できなかったものを「残り」と書く、など。
- 変更の記録の形「現在値 → 候補値、目的、影響する技、検証結果」。
- 実機の計測の出し方（機種・OS・版を付ける、平均と p95 と 100ms 超の回数）。そのための計測を今回入れた。
- 武器アイコンは確定した 3D から描く、操作の記号は SVG、文字は画像に焼かない。

**保留（先に決めること・見ることがある）**

- **GLB とリグのファイル化（NP-009〜014、NP-039）**: いまはコードで組んでいる。Blender はこの作業環境で動かせる（`pip install bpy`）ので GLB の書き出し自体はできるが、形・重み付け・動きの作り直しになる。**狩猟が再読込まで通ってから**、見た目を上げる手段として判断する。骨と socket の名前は計画どおりなので、後から移れる。
- スタミナの候補値、画質の段階と自動調整、KTX2 / Meshopt / Draco: 実機の数値を見てから。配信物は 2.7MB なので、圧縮は当面要らない。
- Service Worker: 入れない（計画も必須にしていない）。
- WebGL のコンテキスト喪失からの復旧: 未対応。実機で起きたら対応する。
