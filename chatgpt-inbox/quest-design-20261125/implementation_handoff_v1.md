# Claude向け クエスト設計の実装引き継ぎ

対象: `kamamon/Kari` / 基点 `v0.21.0`・`9a5443ab1ac813512deac03422ee996f57f8a900`
この提出は設計資料であり、公開コード・ゲームデータを変更していない。参照と算術の検査は、ゲームの動作確認・試遊の合格を意味しない。

## 1. 最初に確認するもの

- `quest_system_v1.md`: 星1〜8、時間、報酬、導入方針。
- `current_quest_overrides_v1.json`: 既存24件の文章・星・時間差分。
- `quest_catalog_v1.json`: 全102件。現行24件、将来種66件、新設主線12件を区別する。
- `story_quest_map_v1.json`・`progression_v1.json`: 主線14本と将来の任意解禁。主線2本は既存IDを再利用する。
- `campaign_support_v1.json`: 工房からの一度限りの材料支給。
- `source_manifest_v1.json`・`validation_report_v1.json`: 参照基点と、実施済み／未実施の確認範囲。

着手時に最新mainとの差を確認する。別の武器・防具・物語案が採用されていれば、現行レシピと支給数量、主線の対応を再照合する。設計JSONを、そのまま`content.json`の読み込み先へ追加しない。

## 2. 導入する順序

### A. 既存24件の文章と星を表示する

1. 星、依頼人、依頼本文、クリア目標時間の型・検証・表示を追加する。星は1〜8の整数。クリア目標時間は試遊前の設計値として扱い、制限時間と区別する。
2. 既存のID、標的、頭数、`kind`、`rankId`、`requires`、支給品、報酬、力尽き回数、帰還待ちは維持する。星から`rankId`や個体能力を自動変更しない。
3. 受注一覧、受注中の情報、結果画面で依頼名と星が食い違わないようにする。既存セーブの達成回数・受注可能範囲は変えない。
4. おすすめ順は表示として追加する。現在受けられる依頼を、星や物語条件で再ロックしない。

主な接続先: `src/data/schemas.ts`、`src/data/validators.ts`、`src/ui/base.ts`、`src/app.ts`の`sessionInfo()`、`src/ui/result.ts`。

### B. フィールドの制限時間を明示する

推奨は`fieldTimeLimitTicks`の追加。フィールド使用中で値があれば**そのまま**採用し、省略時だけ従来の`timeLimitTicks × field.timeLimitScale`を使う。単一区画のarenaでは従来の`timeLimitTicks`を使う。

- ガルドロス中級・上級・極級のフィールドを35・40・45分へ延長する。最終tickは126,000・144,000・162,000。
- 推奨方式では元tick54,000を保ち、arenaは15分のまま。他の21件も現行時間を維持する。
- UIとシミュレーションは同じ時間解決関数を使う。追加値は有限の正整数として検証する。
- 現行倍率を使う代替案とは二者択一。代替案では元tick63,000・72,000・81,000となり、arenaも17分30秒・20分・22分30秒へ変わる。この方式では分単位の丸め表示も直す。両方式を同時適用しない。

主な接続先: `src/game/field.ts`の`questTimeLimitTicks()`と、それを使う受注画面・`Simulation`。

### C. 主線を段階的に接続する

ST01は`quest.basin.003`、ST02は`quest.selvark.r1`を再利用する。どちらを先に達成してもよく、両方の保存済み達成記録でST03へ進む。ST03〜ST14は新規12IDで、既存の自由依頼を置き換えない。

依頼の戦闘、指定狩場、会話・帰還報告、報酬、次節の材料支給が揃った章だけ受注可能にする。本来の湿原や海岸を、名称だけ変えた盆地で代用しない。主線の情報は成功報告として確定させ、捕獲／討伐、希少素材、部位破壊の抽選に依存させない。

新設78件の設計データにある`supplies`は、回復液5・研磨石3。`captureSupplyAdditionsIfImplemented`は、捕獲を採用・実装・検証した依頼だけ拘束罠1・鎮静玉3を追加する指定である。討伐専用種では追加しない。実行用`QuestDef.supplies`へ変換する段階で確実に反映する。**現行実装では`supplies`省略は支給なし**であり、本筋の資金計算は毎回の消耗品支給を前提にしている。既存24件の支給品は変更しない。

### D. 工房の材料支給を一度だけ保存する

`campaign_support_v1.json`の各`packId`を永続的な受領IDにする。受領資格と未受領を確認し、素材加算と受領済み記録を**同じ保存トランザクション**で確定する。回数上限で古い記録が消える狩猟run履歴だけを、永久の受領済み判定に使わない。

ST01＋ST02、ST04、ST08、ST13の達成後に、それぞれ2・3・4・5段目への材料を支給する。数量は「任意の武器1系統＋防具5部位」の段階強化用。7武器全てを同時強化する量ではない。装備を勝手に持ち替えず、通常の工房で強化させる。各段の費用は520／1,650／3,650／7,300、累計13,120。主線を各1回成功し、追加購入をしない条件で通貨が足りる設計である。

既存セーブでは、受領記録が無いことを未受領として安全に移行し、保存済みの達成記録で資格を判定する。再表示、連打、保存失敗後の再試行、再狩猟で二重支給しない。クエストの反復固定報酬へ混ぜない。

## 3. 正本と生成器

大型11件・群れ9件は`tools/gen-monsters.py`の生成物である。生成済み`quests_creatures.json`・`quests_herds.json`だけを書き換えると再生成で戻る。文章・星・最終表示時間を保持する編集用正本を一つ定め、生成器または読み込み側から利用する。ガルドロス4件も同じ管理方針へ揃える。

依頼IDは保存との接続キーとして維持する。設計JSONの`targets`は全件共通の記述形式であり、実行用フィールドへの直接コピーは禁止。単体大型は`targetMonsterId`を使い、実行用`targets`は省略する。

## 4. 現行エンジンの境界

- `hunt`は単体大型の討伐または捕獲、`slay`は討伐。捕獲専用の「倒したら失敗」は未実装。
- 実行用`targets`配列は幼体の群れ専用。大型を入れるとvalidatorが拒否し、生成処理も単体大型とは別経路になる。
- 大型2頭同時、連続大型、大小両方の必須目標、採集・護衛は新機能。今回の文章追加で実装済みにしない。
- 他大型11種には上位素材表がない。物語の中級・上級個体は、能力・素材表を別途準備する。将来種の基礎値と`rankId`倍率を二重に掛けない。
- `requires`は全件AND。将来の「候補5件から異なる2件」やOR条件を配列へ押し込まない。新しい条件型と循環検査を別途実装する。
- 捕獲未対応を選んだ種では、成功条件・目標文・支給品・UIを討伐へ揃える。未実装の治療薬や追跡機能を利用可能として案内しない。

## 5. 受け入れ時の確認

設計の再検査とゲーム実装の検査を区別する。既存の`npm run check`を使い、次の具体的な変更リスクを確認する。

1. **保存互換**: 既存IDの達成回数、旧24件の受注条件、所持品・装備が維持される。ST01・ST02を逆順で達成しても同じ主線へ進む。
2. **時計**: 受注画面とシミュレーションの最終tickが一致。推奨方式では上位3件が35／40／45分、arenaは15分。他21件、ポーズと復帰、制限到達時の失敗も確認する。
3. **支給と受領**: 新規主線に回復・研磨が支給され、捕獲を採用した依頼だけ追加品が付く。章の材料支給は未達成時に付かず、再試行・再読込後も一度限り。保存失敗を成功表示しない。
4. **生成と参照**: 生成器の再実行で文章・星・時間が戻らず、IDの重複・未解決参照・解禁循環がない。準備前の新依頼を受注可能にしない。
5. **目標判定**: 討伐と捕獲を採用した主線では、どちらでも同じ物語成果へ進む。群れの種別頭数を維持し、大型へ群れ用配列を誤用しない。
6. **試遊**: 適正装備と7武器で実際の所要時間・被弾・勝敗を確認する。iPhoneで星・目標・時間・本文が読めるか確認する。資料の算術検査を、この試遊の代わりにしない。

## 6. 提出時点の留保

時間、星、報酬は初期提案であり、実戦の難度は未確定。新しいschema・UI・時計・主線・材料支給は未実装。採用した差分と実際に確認した結果を分けて報告し、未実施の項目は未確認として残す。
