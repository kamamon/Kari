### 2.3 看板のランクと地理

看板制作側の原種案は `monster.orzelion`、中級 `rank.2`、主生息地は**鉛雲高地**。TQ07を中級終盤の任意の初対峙とする。TQ04・TQ06は物語・自由依頼用の極級個体 `rank.4` を別調整する提案であり、原種の初出ランクを上書きしない。原種の基礎値に極級相当の上乗せ値を入れ、さらに `rankId` の倍率を二重に掛けない。

「鳴天の背」は**鉛雲高地内の広い休息棚と点検路の小区域案**。重霧環谷の上方として登録しない。ST14によって谷側の作業と帰路を確保した後、輸送隊が高地の点検へ進める構成とする。二地域の接続は予定輸送路であり、同じ水路の上流下流として直結させない。標高・距離・移動時間・高地側の区域境界は地形設計が必要。

オルゼリオンは雷雲全体を作る存在にしない。休息路を塞がれると深く追い、嵐の前には飛行を切り上げる生き物という設定を守る。四肢は翼腕2・後脚2、冠角2、翼前縁2条、尾先3枚。雷の予兆は胸の二度の膨らみから翼の二条へ流れる。本文と絵で前脚を余分に足したり、普段から全身を発光させたりしない。

雷属性と麻痺の蓄積は別。看板の全雷攻撃へ一律に麻痺を足さない。テンガロは登録上 `elements: [none]`、痺液管による麻痺であり、雷器官の比較対象へ書き換えない。天鳴晶は希少報酬候補で、本筋の証拠・補修条件・最終解禁条件から外す。

## 4. 物語runtimeの拡張で必要な3点

### 4.1 出発前の場面にも前提条件が必要

現行 `src/data/story.ts` の `unlockRules()` は、遊べる章の `openScene` と全 `briefScene` を無条件に解禁する。このまま未来章を公開すると、帰還記録から終盤の説明を先に読める。`storyView()` の「次の狩り」が先頭の未達を選ぶことだけでは防げない。

実装では、章の開始条件とステップの受注条件から、同じ解禁判定を共有する。案は以下のとおり。これは現行スキーマのフィールド名ではない。

- 開始場面: `requiresQuestClears` をすべて満たした時に読める。序章と既存第1章の出発前だけは従来どおり初期公開。
- 出発前場面: 当該ステップの主線前提が保存済みで、内容が準備済みの時に読める。
- 帰還場面: 対応クエストの成功保存済みで読める。
- 章報告: その章の必須ステップがすべて保存済みで読める。任意TQ01〜TQ03・TQ07を含めない。
- 終章: TQ04の成功保存済みだけで読める。TQ05・TQ06の未達で未完了扱いに戻さない。

`requires` は現行では全件AND。OR条件や候補中いくつか、contentReadyなどを既存ID配列へ混ぜない。提案データで表現した条件を、明示した新しい型と循環検査へ変換する。

シーンの読み返し一覧と章カードにも同じ解禁条件を適用する。最終戦の画・標的の正体・真相のまとめを、一覧のサムネイルや要約から先に漏らさない。物語の前半から看板の名前を見せる方針と、真相を隠す方針は別である。

### 4.2 未実装章の形を壊さない

現行 `validateStory()` は `playable:false` の章に steps・openScene・reportScene があるとエラーにする。また、すべてのステップのquestIdに実在クエストを要求する。従って本提出の未来台本を、そのまま `public/data/story.json` へ格納しない。

採用時は、提案原稿を資料として保持し、地域・依頼・会話・報酬が揃った章だけ実行データへ変換する。未完成章は従来の章名・目的のみの予告形式を維持する。公開可能な区間が飛び飛びになる場合、前章の不足を飛ばして「次の狩り」に終盤を出さない。

### 4.3 読むだけの終章を正しく扱う

現行validatorは `playable && no > 0 && !steps.length` を拒否するため、既存ch9を読むだけとして `playable:true` にすると失敗する。採用案は、章種別を読むだけ／依頼ありに分け、読むだけの章にも明示的な前提条件を持たせる拡張。追加決戦の成功によりch9が読め、章の状態は「終章を読んだか」ではなく主線の成功から決まる。

最小導入として最終クエストの報告場面に終章を含める方法もあるが、採用した方法を台帳へ記録する。見せかけのクエストや架空のクリア回数でvalidatorを通さない。現行画面の「次が無い→まだ遊べません」という表示も、制作途中と物語完了で分ける必要がある。

## 5. 保存と再閲覧の契約

### 5.1 初版は保存版5の達成数を正本にする

`src/save/profile.ts` の現在の保存版は5。`progress.questClears` に成功回数、`settledRuns` に直近300件の精算run、`claims` に永久に一度だけの受領を記録する。既読や返答は保存しない。`src/app.ts` は結果保存成功後に解禁場面を計算し、帰還後に開く。

初版の主線は既存の達成数から決められる。会話の完走、選択肢、画像の読み込み完了、ムービーの最終フレームを進行条件にしない。閉じる・スキップ・ページ再読込でも成功済みの仕事は失わず、記録から読めるようにする。

現在の `pendingStory` と討伐／捕獲の `runOutcome` はメモリ上の値で、ページを閉じた後に未読報告を自動再生する永続キューではない。本提出では、その自動復元を完成済みとしない。初版は保存済み成功をもとに記録へ確実に残し、再閲覧は中立文を使えば成立する。

### 5.2 報酬・納品・一度限り狩猟

TQ03の原価減算・報酬・達成数・受領済みclaimsは、同じ保存トランザクションで確定する。書き込み直前に在庫・容量・受領済み・revisionを再検査する。連打、別タブ、保存失敗の再試行で片方だけ成立させない。永久受領を300件で失われるsettledRunsへ載せない。現行DeliveryDefは納品IDをclaimsとquestClearsの両方へ記録するため、TQ03も正式納品IDを共通キーにする。別のclaim専用IDへ分離しない。新しい予備品2種の保護残数keepは0の提案とし、必要量を超えて手持ちを要求しない。

TQ04は一度限りの物語個体とし、初成功後の反復はTQ06へ分ける。この受注制御は現行の `questUnlocked()` に無く、同関数だけを前提条件ANDのまま使って完成扱いにしない。UIと `App.startHunt()` の両方で受注可否を共有し、失敗・リタイア後は再挑戦でき、成功保存後にだけ閉じる。重複runの精算は従来のrunIdで防ぐ。最終戦の演出や記録の再閲覧は、クエスト再受注とは別にする。

TQ06の反復では戦闘個体と戦利品だけを初期化し、主線・claims・改修済みの見た目を戻さない。TQ07で狩る中級個体はTQ04の個体と別なので、任意の討伐後に同じ個体が蘇る台詞にしない。

### 5.3 討伐／捕獲と中立文

捕獲可能と未確認のまま `hunt` を公開しない。拘束・鎮静・個体の衰弱条件・報酬・UI・帰還後の収容先まで揃う場合に `hunt`、揃わなければ当面 `slay` とし、目標・依頼文・支給品を統一する。討伐版を採用しても、物語上の安全確保・観測結果・終章は等価とする。

帰還直後だけ結果別の一文を出せる。記録の読み返しでは「点検班が入れる区間を確保した」のように双方に成立する文を使う。捕獲時に「亡骸から」、討伐時に「運び出した生体から」という矛盾を残さない。必須証拠は勝利の固定成果であり、天鳴晶の抽選や翼の破壊を条件にしない。

### 5.4 将来storyEffectsを永続化する場合

灯の増減、部品交換、通行路の切替は、初版では場面絵と作業班の報告で表現する。マップの見た目を変えるなら、成功保存済みのクエストから状態を再計算すればよい。会話を読んだ順序で設備が変わる仕様にしない。

派生計算で足りず `storyEffects` 等を保存へ追加する場合は、新保存版・移行・トランザクションを別途設計する。

1. 単調な効果ID（例: 高地の点検路確保、予備品受領）と対応する成功条件を定義する。演出再生回数と混同しない。
2. 既存版からの移行では保存済みのクエスト達成・claimsだけを根拠に効果を補い、未受注の仕事を達成扱いにしない。
3. 新成功の報酬・達成数・恒久効果は同一トランザクションで確定する。保存に失敗したら視覚上だけ完成させない。
4. 未知IDを捨てず、新版セーブを旧版で上書きしないという現在の方針を維持する。
5. 場面のスキップ・再閲覧・日夜の演出変更は恒久効果を増減させない。画面初期化時は保存から同じ状態を再構成する。

## 6. 受付・難度・時間・報酬

星と級と戦闘倍率を分ける。級別受付と星ごとのまとめ表示が別作業で入る場合、本台帳の `receptionGrade`、`stars`、`boardLane` を正本IDへ対応させる。TQ04の受注は保存済みST14と制作依存の完成による。さらに別ルートの昇級周回を要求しない。受付への物理アクセス解禁を主線で行う場合は、自由依頼側の現在の資格も保持する。

TQ03は里で完結する納品窓口へ置き、出発・狩猟時計・力尽き回数を使わない。既存 `timeLimitTicks:0` で無制限を代用しない。納品確認画面は原価と残数を示す。

TQ01/TQ02/TQ05は `gather` 経路の提案。必要品は確定採取し、必要量より多い到達可能な点を用意する。今回のrunの採集袋だけを数え、在庫や支給品を混ぜない。必要量を納品時に消費し、余剰のみを報酬へ移す。エリア往復で採取点を再生しない。敵なしの採取であることを表示し、星の高低のために不意の雷・落下死を付け足さない。極級★7のTQ05は移動量込みの暫定値で、試遊による再評価が必要。

現行 `questTimeLimitTicks()` は `fieldTimeLimitTicks` があればその値を使用し、無い場合だけ `timeLimitTicks × field.timeLimitScale` を計算する。新依頼の最終フィールド時間は、20分=72,000、25分=90,000、35分=126,000、45分=162,000 tick（60Hz）。arena側の値は今回固定していない。フィールド時間へ倍率を二重適用しない。

報酬・数量は未試遊の提案値。`proposal.material.*` は正式な所持品IDではない。看板の「鳴天竜の蒼甲」という名称は制作側から参照したが、中級と極級の段階別ID・報酬表は登録担当が確定する。同じ提案素材名だからといって、中級TQ07から極級用素材を先取りさせない。採用時は各クエストの戦闘ランクに一致する正式IDへ解決する。

必要な補修材料は里の作業班が本筋として確保する。TQ03の在庫納品は、その後の点検用の予備品である。必須の工房材料支給（ST01+02、ST04、ST08、ST13の節目）を任意納品へ取り上げない。新装備・技能の採用後は、既存支給で適正装備へ到達できるか経済と難度を再点検する。

## 7. 原画・台詞・演出の取り込み

原版PNGは制作資料として保持する。場面背景は現行の `src/ui/artIndex.ts` の `STORY_ART` と `storyArtUrl()` へ登録する必要がある。現行の配信背景は1280×720 WebPで、PNGの存在だけではUIから参照できない。登録キー・実ファイル・台本の参照が一致することを確認する。

新表情はspeaker.facesとPORTRAITSへ登録する。話者は既存 `minagi`、`isane`、`rokuha`、`senaki` を利用する。台詞のないカメラ移動・無人の遠景・環境音指示は `StoryLine` にそのまま入れない。現行validatorはchoices以外のwho無し台詞を拒否するので、演出表と台詞データを分けて変換する。

初遭遇の見せ場は、姿と予兆を読むための短い演出にする。スキップした場合も同じ地上姿勢・安全な距離で操作が始まり、画面外の即時雷撃を受けない。雷の眩しさを下げても、胸の膨らみ・翼板の動き・姿勢と音で予兆を読める設計を維持する。台詞を読む間は時計と入力を止め、閉じた後に押しっぱなし入力を持ち越さない。

環境の昼夜や天候は初版では固定した場面設定でよい。全世界の日夜時計や天候AI、実際に水を流す装置操作を今回の台詞から自動実装したことにしない。BGMと鳴き声は別のオーディオ制作へ、必要場面・尺・開始終了条件を台帳で渡す。

## 8. 取り込みの順序

1. **正本照合。** 最新main・看板の採用版・級別受付の作業を読み、今回の提案IDと正式IDの対応を確定。受領した原画と素材台帳の参照を照合する。
2. **物語の解禁修正。** 前章ゲートと読むだけの終章、制作途中と完了の表示を分ける。既存序章・第1章の挙動を維持する。
3. **既存主線の後半を地域ごとに採用。** ST03以降の本来の地域、敵、報酬、固定帰還報告が揃った章だけ有効にする。
4. **中級の看板接続。** 原種rank.2と鉛雲高地が揃ったらTQ07を任意公開できる。本文・型・捕獲可否・反撃時間を合わせる。TQ07を本筋の必須条件へ変えない。
5. **決戦の採用。** ST14と高地への予定輸送路を成立させ、別調整の極級個体・一度限り受注・TQ04帰還報告・ch9を一式で公開する。
6. **任意仕事と反復。** TQ01/TQ02/TQ03は必要地域と素材が揃った範囲で追加。最終戦後にTQ05/TQ06を加え、設備の恒久状態と別個体の説明を維持する。
7. **公開前確認。** 以下の受け入れ条件を変更リスクに応じて確認し、未実施の実機試遊を完了と書かない。採用箇所と残る提案を掲示板へ記録する。

TQ04だけを現在の盆地に置いて名称を鉛雲高地に変える導入はしない。将来の地域を文章だけで遊べるものにせず、依存が足りない間も物語・原画・台帳は制作資料として利用できる。
