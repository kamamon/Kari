## 1. 完了させるもの

**利用者の今回の指示は、2G を標準の採用方針として実装すること。調査資料を受領して候補を整理するだけでは完了しない。** 標準ルールは `classic_hunt_v1` 一つにする。旧技を同じ標準へ混在させたり、旧式と新式を同等の二つの完成品として維持したりしない。旧データは保存・リプレイ・移行記録の互換に用いる。ロックオン、照準補正、操作配置等の補助設定は標準と区別して保持でき、既存利用者の設定を黙って消さない。[D1 §6、D3 §8]

最終対象は、2G 相当の機能役割を備えた武器 11 系統、既存 12 大型・8 幼体の動作と行動、装備・技能・生産・四級の進行、登録済み 20 フィールドである。原画・体型・名前・世界設定は Kari の資産を使い、里の既存 0m／−3m の段差、四級、所持品・達成・外見・受領済み報酬を保持する。既存の高速離脱など、過去の利用者要望も変更点と区別して引き継ぐ。[D1〜D4]

初期の盆地改修では、11 エリアの ID と 14 接続を維持する。新 19 フィールドの `runtime_field_id` は未採番で、`field_blueprints_v1.json` は設計資料である。Claude が既存型と登録先を確認して ID 対応表を作り、実行データへ変換する。JSON を配置しただけで狩場完成とはしない。[D4]

原作の未測定フレーム・速度・倍率を確定値に置き換えない。【原作資料で確認】【映像で観察】【Kari 仮設計】【未検証】を記録に残す。原作の内部値が分からなくても、採用済みの状態・機能・動作構成の実装は進める。数値一致が未確認であることと、機能未実装を別々に管理する。

## 3. P0 で固定する共通契約

- **入力と行動：** 押下・保持・解放、複合入力、命令消費、失効を状態表で決める。照準の向きはシミュレーションへ渡し、描画カメラからその都度推測しない。旧パリィ・自動反撃・兜割り等を互換 ID と標準技表で区別する。[D1 §2〜6]
- **時間とイベント：** 行動 tick、姿勢、移動曲線、攻撃判定、音、効果・消費の確定が同じ時間軸を使う。命中停止と怒りの速度変更で一部だけ先に進めない。描画補間が戦闘結果を変えない。[D1 §4、D2 §3・5]
- **地面と移動：** 共通の高さ取得を、足元Y・支持面・移動モードを伴う問い合わせにし、移動、足の接地、モンスター経路、採取・設置位置、カメラの判断へ接続する。登攀・飛行・降下中は専用軌道が位置を持ち、着地時に支持面へ復帰する。描画エリアを解放しても、別エリアの大型・休眠回復・追跡期限の論理状態は維持する。まず平坦な戦闘床、その外側の狭路、高低差・登攀の順で整え、描画地面と通れる地面を一致させる。[D4]
- **保存と参照：** 装備定義と所持個体、現在行動とリプレイ版、設計用フィールドキーと実行 ID を分ける。schema の次番号は着手時の現行を確認し、03 の「6予定」を無条件に使わない。旧原本・未知 ID・受領記録を保持する。[D3 §8]

装飾品・弾薬・素材・報酬の確定イベントは後の機能でも再利用する。P0 の段階で効果が存在しない技能や未実装狩場を選択可能にして、表示だけ先に完成させない。

## 4. P1 の縦断シナリオ

新規保存と既存保存の両方で、里で装備と道具を確認し、盆地の依頼を受ける。野営地から代表ルートを通り、段差・狭路・広い戦闘床を移動してガルドロスへ遭遇する。抜刀攻撃、溜め、ガード、回避、納刀、回復・研磨を使い、頭・脚・尾を狙い分ける。旋回が終わる前後と突進の方向確定前後で位置を変え、避けた結果が再現することを見る。

通常・怒り・転倒・弱り・退避・休眠を記録し、追跡と道具を使う時間が成立することを確認する。討伐と捕獲は別の実行で確認し、同一実行で両方成立させない。帰還後の素材・消費・部位成果を確認して製作または強化し、再読込後に次の狩りへ持ち出す。この時点は既存の利用可能な生産経路で通し、P3 の新技能・装飾品まで完成したとは報告しない。

通常操作で通した記録を主とする。状態注入は怒りや転倒の境界を効率よく確認する補助に使い、通常プレイでその状態へ到達できた証拠とは区別する。代表狩猟を通せても、全武器・全種・全狩場を確認済みにしない。

## 6. 検証の分担と範囲

実装時の自動検査は、今回変える意味のある境界を中心にする。入力と固定 tick の決定論、当たり判定と姿勢のずれ、保存移行の冪等性、報酬重複、技能の境界、経路到達性を優先する。生成したファイルと同じ値を読んで同じ値か比べるだけの検査を大量追加しない。共通高さ取得や保存の変更では影響する既存検査も実行し、無関係な検査を繰り返して作業を止めない。

外形・動き・操作感は自動検査の合格だけで判定しない。通常カメラの等速録画を主に、判定表示付き録画・低速再生を補助として使う。足の接地、攻撃予兆、敵が画面を占める時の視界、着地や後隙の読め方を確認する。iPhone では指で隠れる範囲、カメラ操作と攻撃の両立、持続操作、回転や中断復帰を確認する。

未実機の場合もコード実装や自動検査の成果は提出できる。ただし「実機未確認」を残し、全体の体験検証完了とはしない。実装の正しさ、原作資料との近さ、iPhone の操作感は別欄で記録する。通信先やブラウザの性能測定値がない時は、推測した FPS・遅延を記入しない。

今回の設計納品では、本体の試験を実施済みと記載しない。文書・JSON の構文や整合、実行環境の確認を行った場合は、その範囲と結果を root の納品記録にまとめる。`npm ci` が成功してもゲームの受け入れ条件を満たした証拠にはしない。

## 7. Claude が返す記録

各段階の返答は次の形式で残す。見た目の画像だけ、変更ファイルの列挙だけで終わらせず、実際に何ができるようになったかを先に書く。

```text

今回できるようになったこと：
要件ID：A01 ...（対象範囲を種・武器・狩場まで記載）
変更ファイル：path — 変更理由・生成元か生成物か
保持した既存仕様・移行した旧仕様：
検証：方法、環境、操作、期待結果、実際の結果、合否
録画：ファイルまたはURL、時刻、通常／判定表示、使用武器・対象・状態
原作比較：作品・機種、資料URL・時刻、観察できた点、未測定値
調整：現行値 → 変更値、Kari仮設計、狙い、比較結果
```

録画には条件を添え、編集でつないだ別実行を一回の狩りと表示しない。原作比較の時刻と Kari の行動 tick を混同しない。同一条件で比較した項目と、違う個体・装備・地形での観察を区別する。

最終返却では A01〜A10 と全対象の実装表を合わせ、未対応を数えられる状態にする。大剣だけの完成、盆地だけの完成、新武器の外見だけ、20 件の設計 JSON だけで全体完了にしない。残件があれば次の実装を続け、作業を小分けにしたことを理由に範囲を縮めない。
